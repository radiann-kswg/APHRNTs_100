# Misskey投稿からの気分傾向 俯瞰機能 — 要件定義と実装計画

> Misskey Botの機能。センパイが普段Misskeyに書いている投稿（ノート）から、気分・生活リズムの**傾向**を俯瞰できるようにする。
>
> **実装状況（2026-09-16時点）**: **Phase 1（収集と集計・段階A）と Phase 2（オンデマンド取得）を実装済み**。Phase 3（定期提示）・Phase 4（段階Bの語彙シグナル）・Phase 5（段階CのLLM要約）は未着手で、着手にはセンパイの判断が要る（[未決事項](#センパイに決めてほしいこと未決事項) 2〜5・7）。実装の入口は[`src/scheduler/post-analysis-task.ts`](../src/scheduler/post-analysis-task.ts)と[`src/analysis/`](../src/analysis/)。運用方針は[AGENTS.md](../AGENTS.md#生活管理cbtサポートの運用方針)にも反映済み。

共通仕様の正典は [AGENTS.md](../AGENTS.md)、安全指針は[生活管理・CBTサポートの運用方針](../AGENTS.md#生活管理cbtサポートの運用方針)を正とする。本ドキュメントはその制約下で成立する範囲だけを定義する。

## 背景と目的

現在、Botが気分の傾向を知る手段は**センパイの自己申告だけ**である。

| 既存の手がかり | 実体 | 限界 |
| --- | --- | --- |
| 日次チェックイン | `daily_checkins.mood`（1〜10の総括値） | 記録が途切れた日は何も分からない |
| 時点記録 | `mood_events`（瞬間値） | 同上。会話が発生しないと残らない |
| 服薬アドヒアランス | `medication_logs` | 気分そのものではない |
| Claudeセッション記録 | `claude_session_notes`（`logs/` 由来） | セッションを開いた日にしか残らない |

そして、**記録が途切れること自体が調子の落ちているサインであることが多い**。現行の傾向検知（[`src/scheduler/trend-nudge-task.ts`](../src/scheduler/trend-nudge-task.ts)）は各半期3件以上のmoodサンプルを要求するため、記録が途切れた期間はそもそも発火しない（＝いちばん見てほしい期間に何も見えない）という構造的な弱点がある。

一方でセンパイは普段からMisskeyに投稿している。投稿の量・時間帯・言葉づかいは、自己申告とは**別の角度からの手がかり**になりうる。

**目的**: 自己申告の代わりではなく、自己申告が途切れたときにも「自分の状態を自分で俯瞰する材料」を増やすこと。

### この機能が主張しないこと（先に確定させる）

- 精神医学的なスクリーニング・診断ではない。妥当性検証を経た尺度ではなく、**センパイ個人の平常時との差分**を眺めるだけの道具である。
- 「投稿が減った＝調子が悪い」のような因果を主張しない（忙しい・出かけていた・別の場所で書いていた、いくらでも理由はある）。
- センパイの代わりに結論を出さない。出力は常に「材料の提示」までで止める。

## 「投稿学習」という言葉の整理（最初に決めるべきこと）

センパイの言う「HTLの投稿学習」は、技術的には3つの別物に分解できる。要件定義が必要になるのは、この3つを混ぜると危険だからである。

| # | 解釈 | 本機能での扱い | 理由 |
| --- | --- | --- | --- |
| 1 | LLMのモデル学習（ファインチューニング・学習データ提供） | **やらない** | 個人の健康情報を外部のモデル重みに残す行為であり、[AGENTS.md 禁止事項](../AGENTS.md#禁止事項)に真っ向から反する。撤回もできない |
| 2 | HTL（ホームタイムライン）の収集＝**他者の投稿**の取り込み | **やらない** | 第三者の投稿は、その第三者の同意なしにセンパイのメンタル分析の材料にしてよいものではない。取得しなければ漏れようがない |
| 3 | **センパイ本人の投稿**の集計・要約 | **これだけをやる** | 本人の同意のもと、本人が自分を俯瞰するために使う。既存の `logs/` 運用と同じ性質 |

本機能で「投稿学習」と呼ぶのは **3 だけ**である。以降このドキュメントでは誤解を避けるため「学習」ではなく**「集計」「要約」**と書く。

### HTLを購読する必要がない理由

センパイが懸念したとおり、HTLを読むと他者の投稿が不可避で混入する。だが**本人の投稿だけが欲しいなら、HTLは技術的にも不要**である。

| 取得口 | 返るもの | 本機能での採否 |
| --- | --- | --- |
| `users/notes`（REST・`userId` 指定） | 指定ユーザーの投稿のみ | **採用**。第三者の投稿が構造的に1件も入らない |
| `notes/timeline`（REST・HTL） | 自分＋フォロー中の全員 | 不採用。本人ぶんを抽出するには他者の投稿を一度プロセスに載せる必要がある |
| ストリーム `homeTimeline` チャンネル | 同上（リアルタイム） | 不採用。理由は同じ。加えて常時接続の購読対象が増え、切断・取りこぼしの面倒も増える |

`users/notes` は `misskey-js@2025.2.0` の型定義で以下のパラメータを取れることを確認済み（`built/autogen/types.d.ts` の `users___notes`）。

```ts
{ userId: string; withReplies?: boolean; withRenotes?: boolean; withChannelNotes?: boolean;
  limit?: number; sinceId?: string; untilId?: string; sinceDate?: number; untilDate?: number;
  allowPartial?: boolean; withFiles?: boolean }
```

つまり**「リノートを除外して本人の投稿だけを、前回の続きから取る」がAPI側の指定だけで成立する**。これが本機能の設計上いちばん重要な前提になる。

## 破ってはいけない原則

実装がどう転んでも守る不変条件。レビューではまずここに照らして差分を見る。

| # | 原則 | 具体的な担保 |
| --- | --- | --- |
| P1 | **本人の投稿しか取得しない** | `users/notes` に `userId=BOT_OWNER_USER_ID` 固定。HTLは購読しない。取得後も `note.userId !== ownerUserId` は破棄 |
| P2 | **オプトイン・既定OFF** | 設定が有効になるまで1件も取得しない。いつでもOFFにでき、OFF時は蓄積済みデータも削除する |
| P3 | **投稿本文をDBに永続化しない** | 取得→正規化→集計をメモリ内で完結させ、SQLiteには数値指標と（段階Cでは）要約文だけを残す |
| P4 | **診断しない・断定しない** | 「うつ」「症状」「診断」等の語を出力に使わない。単一の「メンタルスコア」を作らない |
| P5 | **公開チャネルに出さない** | 分析結果の提示先は一対一チャットと `logs/` のみ。公開ノート・リプライで内容に触れない（既存の週次サマリと同じ扱い） |
| P6 | **監視にしない** | 投稿を根拠にBotから自発的に踏み込まない。危機対応は既存の[危機検知](../src/bot/safety/crisis-detector.ts)の専管領域のまま動かさない |
| P7 | **「学習」しない** | 取得した投稿をモデル学習・ファインチューニング・外部データセットに使わない |

実装での担保（Phase 1・2時点）:

| 原則 | どのテストが壊れたら気づけるか |
| --- | --- |
| P1 | `post-metrics.test.ts`（他ユーザーのノートを混ぜても集計に入らない）、`post-analysis-task.test.ts`（取得口が `fetchUserNotes` のみ） |
| P2 | `post-analysis-task.test.ts`（OFFのとき `fetchUserNotes` が1度も呼ばれない）、`post-trend-tool.test.ts`（OFFへの切り替えで指標とカーソルが消える） |
| P3 | `post-analysis-task.test.ts`（実行後にDBの全テーブルを走査し、本文・CWの文字列が1つも出ないことを確認） |
| P4 | `post-trend.test.ts`（出力に「診断」「症状」等の語が含まれない・合成スコアを作らない） |
| P6 | `post-trend-tool.test.ts`（ツール説明文の「聞かれたときだけ」「話題を切り出してはならない」が消えていない） |

P6について補足する。公開投稿を機械が読んで、本人が求めていないタイミングで「その投稿、気になったんだが」と声をかけるのは、**支援ではなく監視**として体験されうる。ここは機能の有用性より体験の安全を優先し、v1では投稿起点の自発的な介入を一切行わない（段階的な緩和案は[出力とUXの要件](#出力とuxの要件)に記す）。

## スコープ

### やること

- センパイ本人のMisskey投稿を定期取得し、**日次の指標**（投稿数・時間帯分布・文字数・語彙の傾向など）に集計してSQLiteへ保存する。
- 集計結果を、既存の自己申告記録（気分・睡眠・服薬）と**並べて眺められる形**で提示する。
- 提示先は一対一チャット（オンデマンド＋週次サマリの1セクション）と `logs/bot-digest.md`。

### やらないこと（v1で明確に外す）

- 他ユーザーの投稿の取得・分析（P1）。
- 投稿本文のDB保存、および `logs/` への本文の書き出し（P3）。
- 投稿を根拠にした自発的な声かけ・危機介入（P6）。
- 感情分析API・外部SaaSへの送信。段階CのLLM要約を入れる場合も、送信先は既に会話で使っているAIプロバイダ（`src/ai/`）に限る。
- リアルタイム分析。日次バッチで十分であり、常時接続の責務を増やさない。
- 画像・動画・音声の解析（添付の**有無と枚数**だけをメタデータとして数える）。

## データ源の要件

### 取得

- API: `users/notes`、`userId = BOT_OWNER_USER_ID`。`BOT_OWNER_USER_ID` が空のときは**機能ごと無効**（対象を特定できないため。既存の連携ブリッジと同じ考え方）。
- パラメータ既定: `withRenotes: false` / `withReplies: true` / `withChannelNotes: false` / `limit: 100`。
- カーソル: `bot_state` に `post_analysis_last_note_id:<userId>` を持ち、`sinceId` で前回の続きから取る（[`src/bot/replay.ts`](../src/bot/replay.ts) の `replay_last_mention_id` と同じ設計）。Misskeyのidは時系列順の文字列なので辞書順比較でよい。
- 1回の実行で取得する上限を設ける（既定500件＝100件×5ページ）。VMがSpot中断等で長期停止していた場合は上限まで取り、続きは次回に回す（冪等なので取りこぼさない）。
- 実行頻度: 1日1回（既定05:00 JST）。前日ぶんが確定してから集計し、他のスケジュールタスク（朝08:00・服薬18:00・ナッジ21:00・ローカル同期03:00/10:00）と時刻が重ならない枠を選ぶ。

### 取得対象と除外

| 種別 | 扱い | 理由 |
| --- | --- | --- |
| 通常の投稿（本人） | 対象 | 本機能の主対象 |
| リプライ（本人が書いた側） | 対象（本文のみ） | 本人の言葉である。**リプライ先の本文（`reply`）は参照しない** |
| リノート（`renoteId` ありで `text` なし） | 除外 | 他者の言葉であり、本人の記述ではない |
| 引用リノート | 本人のコメント部分のみ対象、引用元（`renote`）は参照しない | 同上 |
| 可視性 `public` / `home` | 対象（既定） | |
| 可視性 `followers` | **未決**（[未決事項 1](#センパイに決めてほしいこと未決事項)） | Botがフォローしていなければそもそも取得できない |
| 可視性 `specified`（ダイレクト） | 除外（既定） | 相手ありきの会話であり、第三者の文脈が濃い |
| チャンネル投稿（`channelId` あり） | 除外（既定） | 場の文脈に強く依存し、本人の状態の指標としてノイズになりやすい |
| `localOnly`（連合なし） | 対象 | 可視性とは別軸。扱いを変える理由がない |
| CW付き投稿 | 対象（CWテキストは本文と別に数える） | CWの使用率自体が手がかりになる |
| 添付ファイル・投票 | メタデータのみ（枚数・有無） | 中身は解析しない |
| 削除済み（`deletedAt`） | 集計から除外 | 消したものは無かったことにする |

### 第三者情報の扱い

取得したノートは、集計に入る前に必ず正規化（マスク）する。

- `@user@host` 形式のメンション、`mentions` / `visibleUserIds` に含まれるID → 除去（「メンションを含む投稿だった」というフラグのみ残す）。
- URL → ホスト名も残さず除去。
- カスタム絵文字記法 `:name:` → 除去（`emojis` のキーは数えない）。
- ハッシュタグ → 本文からは除去し、**除外判定用**にタグ名だけを一時的に使う（[語彙シグナル](#段階b-語彙シグナル辞書ベース)の創作文脈の除外に使う）。

正規化後のテキストは**そのランの集計が終わった時点で破棄**する（P3）。ログにも出さない（`logger.debug` でも本文を出力しない）。

### 「見えている範囲」であることの明示

`users/notes` はBotアカウントから見える投稿しか返さない。フォロワー限定投稿をBotがフォローしていない場合、それらは**黙って欠落する**。出力では必ず「Botから見えている範囲での集計」であることを添え、母数の偏りを隠さない。

## 分析の要件

3段階に分け、**下の段ほど後のフェーズに回す**。段階Aだけでも機能として成立するように設計する。

### 段階A: 行動シグナル（メタデータのみ・決定論的）

本文の意味を一切見ない、数えるだけの指標。誤検知の余地が小さく、テストしやすく、外部送信も発生しない。

| 指標 | 定義 | 何の手がかりか |
| --- | --- | --- |
| `post_count` | その日（JST）の対象投稿数 | 活動量 |
| `reply_count` | うちリプライの数 | 対人的な向き合い方 |
| `night_post_count` | JST 00:00〜04:59 の投稿数 | 睡眠リズムの乱れ |
| `first_post_at` / `last_post_at` | その日の最初／最後の投稿時刻 | 起床・就寝リズム（`daily_checkins.sleep_hours` と突き合わせる） |
| `avg_chars` / `total_chars` | 1投稿あたり／合計の文字数（正規化後） | 言葉数の増減 |
| `cw_ratio` | CW付き投稿の割合 | 言いにくいことを書いた量の代理指標 |
| `max_burst_per_hour` | 1時間あたり最大投稿数 | 連投（高揚・反芻のどちらもありうる） |
| `has_attachment_count` | 添付付き投稿数 | 創作・外出などの活動の痕跡 |
| `silent_days` | 直前の無投稿連続日数 | 途切れの検出（**記録が無い期間を可視化できる唯一の指標**） |

### 段階B: 語彙シグナル（辞書ベース）

小さく透明な日本語辞書で、正規化後テキストの語をカウントする。LLMは使わない。

- 辞書はリポジトリ内に平文で置き（`src/analysis/lexicon.ts` 等）、**センパイがレビューして納得した語だけ**を入れる。ブラックボックスにしない。
- カテゴリ案: 疲労・睡眠（「眠れない」「だるい」「しんどい」）／自己否定（「どうせ」「向いてない」）／肯定・達成（「できた」「たのしい」「進んだ」）。カテゴリごとに「そのカテゴリの語を含む投稿数」を数える（語の出現回数ではなく**投稿数**にして、連投による過大評価を避ける）。
- **比喩の誤検知対策**: 既存の危機検知が「死ぬほど眠い」を踏まないよう語根を辞書に入れていないのと同じ方針を取る（[crisis-detector.ts](../src/bot/safety/crisis-detector.ts) の先頭コメント参照）。単独で多義な語は入れない。
- **創作文脈の除外**: センパイの投稿にはナンバーテールズの創作・キャラクターの台詞が含まれる。「」で括られた台詞、指定した創作タグ（除外タグリストは設定で持つ）を含む投稿は語彙集計から外し、行動シグナルの母数としてのみ数える。**キャラクターの感情をセンパイの感情として数えないこと**は、この機能の精度の核心である。
- 危機語（`CRISIS_KEYWORDS` 相当）は**辞書に入れない**。投稿からの危機検知は行わない（P6）。

### 段階C: 要約（LLM・任意・既定OFF）

段階A・Bの数値だけでは「何があったか」は分からない。週次で、その期間の投稿を既存のAIプロバイダに渡し、**非診断的な要約文を1本だけ**生成する案。

- 既定OFF。有効化は設定＋センパイの明示的な同意が両方揃ったときのみ。
- 送るのは正規化後のテキストのみ（メンション・URL除去済み）。件数・文字数の上限を設ける。
- 保存するのは**生成された要約文だけ**。投稿本文は保存しない（P3）。
- プロンプトに明記する制約: 診断語を使わない／断定しない／数値スコアを出さない／本人に見せる文である前提で書く。
- **これは投稿本文が外部APIへ渡る唯一の経路**である。導入可否はセンパイの判断（[未決事項 3](#センパイに決めてほしいこと未決事項)）。

### 単一スコアを作らない

「メンタルスコア 62点」のような合成値は作らない。理由は3つ。

1. 合成した瞬間に「評価」になり、P4（診断しない）と衝突する。
2. 重みづけの根拠が無い（この用途で検証された重みを我々は持っていない）。
3. スコアが下がった日にセンパイが**自分を責める材料**になりうる。

出力は「投稿数 12件（直近4週平均 8件）」のように、**素の数値＋平常時との差**を並べるにとどめる。

### 自己申告記録との突き合わせ

同じ日付キー（JST `YYYY-MM-DD`）で `daily_checkins` / `mood_events` / `medication_logs` と結合できるようにしておく。相関を主張するためではなく、**並べて表示する**ためである（[.cbt-datas/mood-artifact.md](../.cbt-datas/mood-artifact.md) が気分と服薬を重ねているのと同じ思想）。

## 出力とUXの要件

| 経路 | 内容 | フェーズ |
| --- | --- | --- |
| オンデマンド（新ツール `get_post_trend`） | 「最近の投稿の様子はどうだ？」と聞かれたときだけ、直近N日の指標を返す読み取り専用ツール | Phase 2 |
| 週次サマリ（一対一チャット） | [`weekly-summary-task.ts`](../src/scheduler/weekly-summary-task.ts) の文面に「投稿の様子」を1〜2行追加 | Phase 3 |
| `logs/bot-digest.md` | 「## 投稿の傾向」セクションを追加（`BOT_OWNER_USER_ID` 限定は既存ルールのまま） | Phase 3 |
| Claude Desktop のArtifact | 気分の折れ線に投稿量・深夜投稿比率を重ねる（[mood-artifact.md](../.cbt-datas/mood-artifact.md) の拡張） | Phase 4 |

### 文面のルール

- 100(モモ)の口調は保つ。ただし**評価の言葉を使わない**（「ダメだったな」「よく頑張った」ではなく「こう見えた」）。
- 必ず「Botから見えている範囲の集計であること」「これは診断ではないこと」を短く添える。
- 数値の羅列で終わらせず、最後は必ずセンパイに解釈を委ねる一言で閉じる（既存の傾向ナッジ文面と同じ作法）。
- **記録が途切れている期間を責める文面にしない**（[weekly-reflection.md の注意](../.cbt-datas/weekly-reflection.md)と同じ）。

### 投稿起点の介入について（P6の緩和案・Phase 5以降）

v1では行わない。将来検討するとしても、次の条件を全部満たしたときに限る。

- センパイが**別途明示的に**「投稿から気づいたことがあったら声をかけてほしい」と設定したとき（デフォルトOFFの二段階オプトイン）。
- 声かけ先は一対一チャットのみ、頻度は既存の傾向ナッジと同じ週1回上限。
- 危機語の検知は依然として行わない（危機対応は本人がBotに向けて発した言葉に対してのみ。公開投稿の監視にしない）。

## データモデル案

`schema.sql` は `CREATE TABLE IF NOT EXISTS` で冪等に適用される（既存の運用どおり、マイグレーションスクリプトは不要）。

実際に作られたのは `misskey_post_metrics` だけである（`lexicon_json` / `excluded_post_count` は段階Bの、`post_trend_summaries` は段階Cの器なので、着手時に足す）。現行のスキーマは[`src/storage/schema.sql`](../src/storage/schema.sql)を正とする。

```sql
-- 投稿由来の日次指標。**本文は保存しない**（数えた結果だけを持つ）。
CREATE TABLE IF NOT EXISTS misskey_post_metrics (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id TEXT NOT NULL,
  date TEXT NOT NULL,              -- JSTのYYYY-MM-DD
  post_count INTEGER NOT NULL,
  reply_count INTEGER NOT NULL,
  night_post_count INTEGER NOT NULL,
  first_post_at TEXT,              -- ISO 8601
  last_post_at TEXT,
  total_chars INTEGER NOT NULL,
  cw_count INTEGER NOT NULL,
  attachment_post_count INTEGER NOT NULL,
  max_burst_per_hour INTEGER NOT NULL,
  lexicon_json TEXT,               -- 段階Bのカテゴリ別「該当投稿数」JSON（語そのものは残さない）
  excluded_post_count INTEGER NOT NULL,  -- 創作文脈等で語彙集計から外した件数
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  UNIQUE(user_id, date)
);

-- 段階Cの週次要約（有効時のみ）。生成文のみを保存する。
CREATE TABLE IF NOT EXISTS post_trend_summaries (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id TEXT NOT NULL,
  period_start TEXT NOT NULL,
  period_end TEXT NOT NULL,
  summary TEXT NOT NULL,
  model TEXT NOT NULL,
  created_at TEXT NOT NULL,
  UNIQUE(user_id, period_start, period_end)
);
```

- `user_preferences` に `post_analysis_enabled INTEGER NOT NULL DEFAULT 0` を追加（既定OFF＝P2）。既存の `crisis_hotline_enabled` と同じ扱いで、切り替えは本人の明示的な意思表示があったときのみ。**既存DBには列が増えないため**、[`src/storage/db.ts`](../src/storage/db.ts)の `addMissingColumns()` が起動時に `ALTER TABLE` で補う（稼働中の本番DBを作り直さないための最小マイグレーション。回帰テストあり）。
- カーソルは `bot_state` の `post_analysis_last_note_id:<userId>`（キーの組み立ては `postAnalysisCursorKey()`）。集計対象外のノートも含めた最大IDまで進める（除外分を戻すと毎回同じものを取り直し続けるため）。
- **保持期間**: 指標180日（`POST_ANALYSIS_METRIC_RETENTION_DAYS`）。超過分は日次タスクの冒頭で削除する。要約365日は段階C着手時に足す。
- **停止時の削除**: `post_analysis_enabled` を0にしたら、そのユーザーの `misskey_post_metrics` とカーソルを**その場で削除**する（`set_post_analysis_preference` ツール内で実施）。「止めたのにデータは残っている」状態を作らない。
- 日付指定の部分削除（「あの日の分は消して」）は未実装。全消しはツールから即できるため、必要になってから足す。

計画時の案からの差分（意図的な単純化）:

- `post-normalizer.ts` は独立させず `post-metrics.ts` に同居させた。正規化は数十行で、利用者も日次集計だけであるため、ファイルを分ける理由が無かった。創作文脈の判定は段階B（Phase 4）まで不要なので入れていない。

## 設定（`.env`）案

| 変数 | 既定 | 意味 | 状態 |
| --- | --- | --- | --- |
| `POST_ANALYSIS_ENABLED` | `false` | 機能全体のスイッチ。`BOT_OWNER_USER_ID` が空なら `true` でも動かさない | 実装済み |
| `POST_ANALYSIS_HOUR` | `5` | 日次バッチの実行時刻（JST） | 実装済み |
| `POST_ANALYSIS_MAX_NOTES_PER_RUN` | `500` | 1回の実行で取得する上限 | 実装済み |
| `POST_ANALYSIS_VISIBILITIES` | `public,home` | 集計対象の可視性 | 実装済み |
| `POST_ANALYSIS_METRIC_RETENTION_DAYS` | `180` | 指標の保持日数 | 実装済み |
| `POST_ANALYSIS_EXCLUDE_TAGS` | （空） | 創作文脈として語彙集計から外すハッシュタグ | 未実装（Phase 4） |
| `POST_ANALYSIS_LLM_SUMMARY_ENABLED` | `false` | 段階C（LLM要約）の有効化 | 未実装（Phase 5） |

**環境変数（`POST_ANALYSIS_ENABLED`）と本人のオプトイン（`user_preferences.post_analysis_enabled`）は別物**で、両方が揃わないと1件も取得しない。前者は運用者が機能を積むかどうか、後者はセンパイが自分の投稿を数えさせるかどうかを決める。

また、ツール（`get_post_trend` / `set_post_analysis_preference`）は `BOT_OWNER_USER_ID` 本人にしか反応しない。日次バッチが集めるのはオーナーのぶんだけなので、他ユーザーに「有効にした」と答えて何も溜まらない状態を作らないためである。環境変数がOFFのときも同じく「扱えない」と答える。

`.env.example` には、既存の項目と同じく**何を送るのか・何を保存しないのか**をコメントで明記する。

## テスト方針

既存の方針（純関数へ寄せて vitest で検証、実装に対してテストが同規模以上）を踏襲する。

- **純関数のユニットテスト**: 正規化（メンション・URL・絵文字の除去）、創作文脈の除外、日次集計（JST境界・深夜帯の切り方）、期間集計、語彙カウント。
- **JST境界**: 既存の `toJstDateString` の注意点（UTCで切るとJST 0〜9時の実行で窓が1日ズレる）をそのまま踏む。23:59 と 00:00 の投稿が別日になること、深夜帯（00:00〜04:59）の境界値をテストに入れる。
- **プライバシーの回帰テスト**（この機能の要）:
  - OFFのとき `fetchUserNotes` が1度も呼ばれない。
  - 他ユーザーIDのノートが混入しても集計に入らない。
  - 保存後のDBに本文の断片が残っていない（全テーブルを走査して既知の文字列が出ないことを確認する）。
  - OFFへの切り替えで全行が消える。
- **スケジューラ**: `MisskeyClient` をモックし、カーソル前進・冪等性（同じ日に2回走らせても指標が二重にならない）・上限打ち切りを検証。
- **文面**: 出力に禁止語（「うつ」「診断」「症状」等）が含まれないことをテストで固定する。

## リスクと緩和策

| リスク | 影響 | 緩和 |
| --- | --- | --- |
| 創作ロールプレイ投稿をセンパイの感情として数える | 傾向が丸ごと信用できなくなる | 台詞・創作タグの除外、除外件数を指標に含めて可視化、段階Bは Phase 4 まで本採用しない |
| 「見られている」感覚 | 自由に投稿できなくなる＝生活の質を下げる本末転倒 | オプトイン既定OFF、投稿起点の介入なし（P6）、いつでも停止＋削除 |
| 第三者の投稿・個人情報の混入 | 他者のプライバシー侵害 | HTLを購読しない（P1）、リプライ先・引用元を参照しない、メンション/URLのマスク |
| 投稿本文の外部送信（段階C） | 機微情報が外部APIへ渡る | 既定OFF、明示同意、正規化後のみ送信、要約だけ保存 |
| 数値の独り歩き | 「投稿が減った自分はダメだ」という解釈を招く | 単一スコアを作らない、素の数値＋平常時との差だけを出す、文面のルール |
| API負荷・レート制限 | Botの他機能に影響 | 1日1回・上限付き・カーソル方式。失敗時はスキップして次回に回す |
| VM（Spot）の中断 | 集計の欠落 | カーソルで再開、冪等なupsert。長期停止後は上限まで取って残りは翌日 |
| 可視性による母数の偏り | 傾向の誤読 | 「見えている範囲」であることを出力に必ず明示 |

## センパイに決めてほしいこと（未決事項）

Phase 1・2 は、**回答が無くても安全側の既定で成立する範囲**だけを実装してある。現在の扱いを各項目に付記する。

1. **フォロワー限定投稿を集計対象に含めるか**（含めるならBotアカウントがセンパイをフォローしている必要がある。既定は `public` / `home` のみ）
   → 現状: 既定のまま `public,home`。含めたくなったら `.env` の `POST_ANALYSIS_VISIBILITIES` に `followers` を足すだけでよい（コード変更は不要）。
2. **創作アカウント・創作投稿の切り分け方**（同一アカウントでキャラの台詞も投稿しているか。除外に使えるハッシュタグはあるか）
   → 現状: 段階B（語彙シグナル）を実装していないため影響なし。**Phase 4 の着手条件**であり、回答と辞書レビューが揃うまで着手しない。
3. **段階C（LLM要約）を許容するか**（投稿本文が外部APIへ渡る唯一の経路。既定OFFで、Phase 5 を着手しない選択もある）
   → 現状: 未実装。投稿本文が外部APIへ渡る経路は**1本も無い**。
4. **分析結果をどこまで見たいか**（聞いたときだけ／週次サマリにも載せる／`bot-digest.md` にも出す）
   → 現状: **聞いたときだけ**（`get_post_trend`）。週次サマリ・`bot-digest.md` には一切出していない。
5. **傾向ナッジ（既存の声かけ）に投稿由来の指標を反映させるか**（現行は気分低下＋服薬ギャップの両立でのみ発火。ここに触れるかどうか）
   → 現状: **触っていない**。`trend-nudge-task.ts` の発火条件は変更していない。
6. **保持期間**（指標180日・要約365日の既定でよいか）
   → 現状: 指標180日の既定のまま（`.env` で変更可）。
7. **どこから着手するか**（Phase 1 だけ先に作って数週間ぶん溜めてから見え方を決める、という進め方も可能）
   → 現状: Phase 1・2 のみ実装。数値を数週間ためてから、4・5（見せ方・声かけ）を決める進め方ができる状態になっている。
